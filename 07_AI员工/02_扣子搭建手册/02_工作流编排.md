# 扣子搭建手册 · 工作流编排

> 对应 `00_总览_搭建顺序.md`。
> 三条工作流：**主生产链**（手动触发）· **质检回环**（自动）· **定时触发**（自动）。

---

## 一、先说清楚：不要一上来就做全自动工作流

最常见的失败模式：建了 15 个节点的工作流，跑一次要 8 分钟，中途某个节点输出格式变了，后面全崩，调试要逐个节点点开看。

**正确的做法：先手动串一遍，再自动化。**

```
阶段一（Day1-2）  手动串：选题 → 拆解 → 撰稿 → 质检 → 改稿 → 去AI味
                   每个 Bot 都单独测过，输出格式稳定

阶段二（Day3-4）  拆成 3 条工作流，每条只做 2-4 个节点

阶段三（Day5+）   加定时触发、加条件分支、加人工闸
```

**每加一个自动化节点，就手动跑一遍确认没坏。** 别攒着一起调。

## 二、工作流一：主生产链（手动触发）

### 2.1 节点结构

```
【开始】
  │输入：选题（文本）、真实经历（文本，可空）、目标平台（文本）
  ▼
[节点1 拆解官]  ← 大模型节点，调用 A06
  │  输出：骨架
  ▼
[节点2 撰稿官]  ← 大模型节点，调用 A07
  │  输出：初稿 + 10个标题
  ▼
[节点3 质检官]  ← 大模型节点，调用 A10
  │  输出：质检报告
  ▼
[节点4 条件分支] ← 判断节点
  ├─ 【通过】──────→ [节点5 结束] 输出定稿候选
  └─ 【打回】──────→ [节点6 改稿官] → [节点7 去AI味官] → [节点8 质检官复检]
                                                    │
                                                    ▼
                                              [节点9 结束] 输出待人工确认稿
```

### 2.2 节点参数表

| 节点 | 类型 | 调用 | 输入变量 | 输出变量 | 模型/温度 |
|------|------|------|---------|---------|----------|
| 开始 | 开始 | — | 选题 / 真实经历 / 目标平台 | — | — |
| 1 拆解官 | 大模型 | A06 | `ref_articles`=选题, `topic`=选题 | `skeleton` | V3 / 0.3 |
| 2 撰稿官 | 大模型 | A07 | `skeleton`=节点1.skeleton, `my_experience`=开始.真实经历, `platform`=开始.目标平台 | `draft`, `titles` | V3 / 0.8 |
| 3 质检官 | 大模型 | A10 | `draft`=节点2.draft, `platform`=开始.目标平台 | `qc_report`, `verdict` | R1 / 0.2 |
| 4 分支 | 条件 | — | `verdict`=节点3.verdict | — | — |
| 5 结束 | 结束 | — | — | `result`=节点2.draft | — |
| 6 改稿官 | 大模型 | A08 | `draft`=节点2.draft, `qc_report`=节点3.qc_report | `revised` | V3 / 0.7 |
| 7 去AI味官 | 大模型 | A09 | `revised`=节点6.revised, `style_card`=知识库检索 | `final` | V3 / 0.9 |
| 8 复检 | 大模型 | A10 | `draft`=节点7.final, `platform`=开始.目标平台 | `qc_report_2` | R1 / 0.2 |
| 9 结束 | 结束 | — | — | `final`=节点7.final, `report`=节点8.qc_report_2 | — |

### 2.3 条件分支怎么写

条件节点的判断依据选节点3 质检官输出的 `verdict` 字段。

质检官提示词里明确要求输出 `【通过】/【打回-违规】/【打回-AI味】/【需人工确认】`，所以判断条件写成：

```
verdict 包含 "通过"  → 走节点5
否则 → 走节点6
```

**注意**：`【需人工确认】` 也会走节点6（改稿），这是对的——但改完之后到节点8复检，复检结果仍然是「需人工确认」的话，输出到节点9，等人处理。

### 2.4 关键：质检官的禁区输入怎么传

**方案 A（推荐，简单）**：质检官节点挂载 KB_禁区，在提示词里写「从知识库检索目标平台相关的全部禁区条目」。

扣子的大模型节点如果挂了知识库，会自动做检索。但**自动检索是 Top-K 召回，不是全量加载**——这有风险。

**方案 B（严谨，但要预处理）**：在质检官节点之前加一个「代码节点」，从本地禁区文件里按平台过滤，把完整文本塞进 `forbidden_rules` 变量。

```python
# 伪代码，实际节点里换成你的数据
def main(platform):
    # 禁区原文（可以内联，或从 API 取）
    all_rules = "..."
    lines = all_rules.split("\n")
    out, keep = [], False
    for l in lines:
        if l.startswith("## ") or l.startswith("### "):
            keep = (platform in l)
        if keep:
            out.append(l)
    return {"forbidden_rules": "\n".join(out)}
```

**我的建议：先用方案 A 跑通，确认质检官能正常判违规后，再升级到方案 B。** 方案 A 的漏召可以在质检报告里人工补，方案 B 是精度优化不是能不能用的区别。

如果用方案 A，**在质检官提示词里加一句**：

```
禁区清单必须逐条比对，不能只抽查
如果检索到的禁区条目看起来不完整，标注「禁区召回可能不完整」并转人工确认
```

这句话很重要——它让质检官自己承认不确定性，而不是假装查全了。

### 2.5 工作流的输出要人看

节点9 的输出变量应该是完整的一段文本，包含：
- 定稿正文
- 候选标题
- 质检报告
- 一句明确提示：**「请人工确认后再进入发布环节」**

**不要在工作流里接发布节点。** 发布是独立的、必须人按下的动作。

## 三、工作流二：定时触发链（自动跑）

### 3.1 三条独立的定时工作流

**别做一条大工作流。** 分开做，某一条挂了不影响另外两条。

| 工作流 | 定时 | 节点 | 输出到哪 |
|--------|------|------|---------|
| 早间采集 | 每天 08:30 | A03 情报官 → A04 素材官 | 情报库 / 素材库 + 一份日报 |
| 选题池 | 每天 08:45 | A05 选题官（读上面产出） | 选题池 + **等你选** |
| 复盘 | 每天 09:15 | A14 复盘官（读昨日 publish_log） | 案例库 + 表现分 |

### 3.2 早间采集链

```
[开始] → [情报官 A03] → [素材官 A04] → [结束]
```

| 节点 | 输入 | 输出 |
|------|------|------|
| 情报官 | `white_list`=对标账号清单, `crawled`=抓取结果（来自定时器或 API） | `intel_cards` |
| 素材官 | `inbox_files`=Inbox 文件列表 | `material_cards` |

> **抓取从哪来？** 扣子的定时触发器本身不能爬网页。三个可行方案：
> 1. 扣子 + 爬虫插件/自建 API（你已有 `browser-automation-cdp` 技能，可做成本地 API）
> 2. 用 GitHub Actions 抓完写入文件，扣子工作流读文件
> 3. **最省事**：情报官每天不自动跑，你自己花 10 分钟把看到的内容丢进 Inbox，让素材官整理

方案 3 是 P1 阶段的推荐做法。自动爬取是 P2 的事。

### 3.3 选题链

```
[开始] → [选题官 A05] → [结束]
```

输出到 `state/选题池.csv`（格式见 `../04_人类工位/state_文件说明.md`）。

**关键设计：选题链跑完就停，不要自动开始写稿。**

选题是判断题，AI 出候选，你选。自动接撰稿就跳过了最重要的人。

### 3.4 复盘链

```
[开始] → [复盘官 A14] → [结束]
```

输入 `publish_log`（昨天发布记录）和各平台数据。

**平台数据怎么来？** 手动导出最实际：
- 公众号后台 → 数据统计 → 导出
- 小红书创作中心 → 数据中心 → 导出
- 抖音创作者中心 → 数据 → 导出

导出后丢进 Inbox，复盘官读。**这比接 API 快得多，且数据更准**（有些平台 API 拿不到完读率）。

## 五、扣子里没有原生定时？用 GitHub Actions 兜底

如果你不熟悉扣子调度，或者想把某些步骤放到本地跑，**GitHub Actions 是很好的补充**。

你已经有三个项目在用 GitHub Actions（coze-daily-credit-action、kzz_txq、ai），基础设施是现成的。

典型分工：

| 任务 | 放哪 | 理由 |
|------|------|------|
| 抓取情报、写文件 | GitHub Actions | 本地跑更自由，文件直接落库 |
| 调用扣子 API | GitHub Actions | 扣子提供 API 调用方式，可以任意编排 |
| 定时提醒 | GitHub Actions + PushPlus | 你已在用这套组合 |

一个最小的调用示例（伪代码，实际接口格式以扣子文档为准）：

```python
# 每天 08:30 触发
import requests

resp = requests.post(
    "https://api.coze.cn/v3/workflow/run",   # 具体地址查扣子文档
    headers={"Authorization": f"Bearer {COZE_TOKEN}"},
    json={"workflow_id": WORKFLOW_ID, "parameters": {}}
)
print(resp.json())
```

**这个先别做。** 手动跑通了再自动化。

## 六、工作流调试顺序（出问题时按这个查）

```
① 先单独测节点
   在节点里点「运行」，看这个节点自己的输出对不对。
   大部分问题在这一步就暴露了。

② 再测两两组合
   拆解官 → 撰稿官。中间的变量映射对不对？

③ 最后测全链
   全链跑一次，看最终输出。

④ 看运行日志
   扣子工作流有运行记录，能看到每个节点的输入输出。
   重点看：哪个节点开始输出格式变了。
```

### 常见故障速查

| 现象 | 最可能的原因 | 处理 |
|------|------------|------|
| 节点输出为空 | 上游输出变量名写错，或上游节点报错 | 逐节点跑，看谁先空 |
| 输出里有「好的，我来帮你」 | 提示词的「风格要求」段没粘全 | 补回去 |
| 质检官说「禁区召回可能不完整」 | 自动检索 Top-K 限制 | 升级到方案 B（代码节点预过滤） |
| 撰稿官输出没风格 | 风格指纹卡没挂上或检索不到 | 检查挂载；检查指纹卡是否被切碎 |
| 变量传过去是「undefined」 | 大小写不一致 | 逐字比对变量名 |
| 分支总是走错边 | 质检官输出格式变了 | 让质检官输出固定字段值，别用自然语言判定 |
| 节点超时 | 提示词太长 + 模型慢 | 拆分节点；或换快模型 |

### 关于分支条件的一个建议

质检官输出的是 `【通过】/【打回-违规】/【打回-AI味】/【需人工确认】` 这种带书名号的中文。

扣子的条件节点做字符串匹配时，**书名号可能造成麻烦**。两个做法：

1. 在质检官提示词里改成分支输出固定英文枚举值：
   ```
   ## 五、判定
   verdict: PASS | BLOCK_VIOLATION | BLOCK_AI | NEED_HUMAN
   ```
2. 或在质检官输出后加一个代码节点做正则提取

**推荐做法 1**——直接在质检官提示词里加一行，让它输出机器可读的字段。但这会影响人工阅读，所以建议同时保留中文说明：

```
## 五、判定
【通过】/【打回-违规】/【打回-AI味】/【需人工确认】
verdict_code: PASS | BLOCK_VIOLATION | BLOCK_AI | NEED_HUMAN
```

两行都给，人看第一行，机器读第二行。

## 七、建工作流的时间预算

| 工作流 | 节点数 | 建+调时间 | 建议时机 |
|--------|-------|----------|---------|
| 主生产链 | 9 | 3-4 小时 | P1（Day3-4） |
| 早间采集 | 3 | 40 分钟 | P2 |
| 选题链 | 2 | 20 分钟 | P2 |
| 复盘链 | 2 | 20 分钟 | P2 |
| 发布适配 | 2 | 30 分钟 | P2 |

**第一天不要建工作流。** 第一天只建 Bot 并单独测。

## 八、一页速查

```
主生产链：开始 → 拆解 → 撰稿 → 质检 → 分支 → (通过)结束 / (打回)改稿 → 去AI味 → 复检 → 结束
定时链：三条独立的小工作流，别合并
发布链：单独一条，人工触发
分支判定：让质检官同时输出中文说明 + 英文 verdict_code

调试：单节点 → 两两 → 全链 → 看日志
```
