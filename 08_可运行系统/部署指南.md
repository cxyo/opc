# 云端部署指南

这份文档记录把「AI 员工控制台」部署到线上��完整步骤和踩过的坑。
照着做能一次跑通。

---

## 一、现在跑在哪

| 位置 | 角色 | 地址 |
|---|---|---|
| GitHub Pages（`cxyo/opc` 仓库） | **前端**（静态 HTML） | https://cxyo.cn/opc/ |
| serv00（Phusion Passenger 托管 Python） | **后端**（真实数据 + SSE） | https://micky.serv00.net/ |

两边配合方式：

```
浏览器打开 https://cxyo.cn/opc/
        │
        │ 页面里的 <html data-api="https://micky.serv00.net">
        │ 所有 /api/xxx 请求自动改写成跨域请求
        │ 口令通过 Authorization: Bearer 头带（不受 SameSite 限制）
        ▼
https://micky.serv00.net/api/xxx  →  真实岗位 / 素材库 / 产出 / 实时事件流
```

**为什么不用 iframe 套壳**：iframe 会被 `X-Frame-Options` 拦，而且页面和后端是两套 URL，
刷新、鉴权、书签都会别扭。直接做成前后端分离更干净。

**为什么不用 Cookie 传口令**：`cxyo.cn` 和 `micky.serv00.net` 是**不同站点**，
Cookie 的 `SameSite=Lax` 策略下跨站请求根本不带 Cookie，浏览器会直接拒绝。
所以改用 `Authorization: Bearer`（后端三种都认，见下文）。

```bash
#      08_可运行系统/     → public_python/08_可运行系统/
#      03_知识库/         → public_python/03_知识库/
#      07_AI员工/         → public_python/07_AI员工/

# 5) 写环境变量（Passenger 只读 ~/.bash_profile，不读 ~/.bashrc / ~/.shrc）
cat > ~/.bash_profile <<'EOF'
export STAFF_CORS_ORIGINS="https://cxyo.cn,https://www.cxyo.cn,https://cxyo.github.io"
export STAFF_ACCESS_PASSWORD="你的访问口令"

# 6) 自检 + 重启
cd ~/domains/micky.serv00.net/public_python
python3 passenger_wsgi.py     # 不报错 = 配置正确
devil www restart micky.serv00.net
```

## 四、访问口令（三种传递方式）

后端 `_authorized()` 同时认这三种，前端按场景选用：

| 方式 | 用在哪 | 说明 |
|---|---|---|
| `Authorization: Bearer xxx` | **跨域首选** | 不受 SameSite 限制，前端存 localStorage |
| `Cookie: staff_pwd=xxx` | 同源部署（本地 / 单机） | 后端自动带上 |
| `?access=xxx` | **EventSource 用** | SSE 不能自定义请求头，只能走查询参数 |

前端逻辑：跨域时把口令存进 `localStorage`，每次 `fetch` 自动加 `Authorization` 头；
`EventSource` 则把口令拼到 URL 查询参数上。

同源部署（`python run.py console`）不受影响 —— 后端直接返回登录页 HTML。

## 五、SSE 实时事件流

这是部署时最容易踩的坑，记录一下：

### 5.1 WSGI 的写法要求

WSGI 协议规定：**先 `start_response`，再返回可迭代对象**。
所以 SSE 的响应头必须在 `start_response` 之前设好，不能等到生成器里才设 ——
否则头部丢失，浏览器拿不到 `text/event-stream` 就不按流解析，表现为「连上了但没数据」。

```python
def _handle_sse(h, collector, start_response, cors=None):
    headers = [
        ("Content-Type", "text/event-stream; charset=utf-8"),
        ("Cache-Control", "no-cache, no-store"),
        ("X-Accel-Buffering", "no"),      # ← 关键
    ]
    start_response("200 OK", headers)
    return gen()                          # ← 生成器，边生成边推
```

### 5.2 三个必需的头

| 头 | 作用 |
|---|---|
| `Content-Type: text/event-stream; charset=utf-8` | 让浏览器按流解析 |
| `X-Accel-Buffering: no` | **serv00 官方文档指定的唯一反缓冲手段**，缺了 nginx 会攒着不发 |
| `Cache-Control: no-cache, no-store` | 禁止缓存 |

### 5.3 心跳

每 15 秒发一条注释行 `: ping\n\n`（注释行不会触发前端的 `onmessage`，
但能防止中间层按空闲超时掐断连接）。

### 5.4 实测结果

```
$ curl -N https://micky.serv00.net/api/live/stream
: connected        ← 0.0s 立即
: ping             ← 15.0s
: ping             ← 30.9s
```

## 六、常见坑速查

| 现象 | 原因 | 解法 |
|---|---|---|
| SSH 认证失败 | 用了 `ssh.serv00.com` | 换 **`s8.serv00.com`** |
| FTP 530 | serv00 FTP 用独立密码体系 | **别用 FTP**，直接用 SSH + SFTP |
| 面板登录 OK 但 SSH 失败 | 面板密码 ≠ SSH 密码 | 面板 `/passwd/` 改主密码，两边统一 |
| Python 应用起不来 | 没建 `passenger_wsgi.py` | 入口文件**必须叫这个名字** |
| 页面 404 | 没删 `public/index.html` | 删掉它 |
| SSE 连上没数据 | 响应头在生成器里设了 | 头必须在 `start_response` 前设 |
| SSE 一直转圈 | 缺 `X-Accel-Buffering: no` | 加上 |
| 403 一堆 | WAF 误杀 | `devil www options <域名> waf 0` |
| 跨域 cookie 存不下 | `SameSite=Lax` 拦跨站 | 改用 `Authorization: Bearer` |
| 应用 24 小时后被回收 | serv00 策略 | 面板 `/cron/` 加个定时请求保活 |
| 改了代码不生效 | Passenger 缓存了 .pyc | `devil www restart <域名>`（注意：重启**不**清 .pyc） |
| git push 极慢/502 | 环境有代理，HTTP/2 不兼容 | `git config http.version HTTP/1.1`，或改用 REST API |

## 九、WSGI 适配层说明

原控制台是用标准库 `http.server` 写的，本机跑得好好的，但托管环境只认 WSGI。
`staff/wsgi_app.py` 是薄适配层，不重写业务逻辑：

| 原实现 | WSGI 版 |
|---|---|
| `self.path` / `self.headers` / `self.rfile` / `self.wfile` | 从 `environ` 还原 |
| `self.send_response` / `send_header` / `end_headers` | 收集成响应头数组 |
| `self.wfile.write(...)` | 收集成响应体字节串 |
| `_sse()` 死循环写 wfile | 改成生成器 + `start_response` |
| `_is_local_request()` 判断 127.0.0.1 | 云端全部视为外部（必须过口令），本机自测用 `STAFF_TRUST_LOCAL=1` 放行 |

本机自测：

```bash
cd 08_可运行系统
STAFF_TRUST_LOCAL=1 python staff/wsgi_app.py
# → http://127.0.0.1:8901/
```

## 十、弱网优化（2026-11-01 实测补）

### 问题现象

线上控制台打开后，素材库一片空白，日志里 `/api/materials/list` 返回 200，
但前端 `await` 一直不 resolve。素材库卡片一个都不出来。

### 根因不是代码，是链路

同一份代码在服务器内部请求只要 **0.06 秒**，从国内用户侧请求要 **18~25 秒**。
测出来这条链路到 serv00 的实际带宽只有 **~8 KB/s**：

| 响应 | 大小 | 耗时 |
|---|---|---|
| `/api/materials/overview` | 468 B | 2.4 s |
| `/api/materials/list` | 214 KB | 24 s |
| 服务器内部同一接口 | 214 KB | **0.06 s** |

应用层解析台账只要 4 毫秒（台账 288 KB，`json.load` 实测 0.004 s），
所以瓶颈既不在读文件也不在序列化，**纯粹是传输慢**。
`serv00` 前面的 nginx 默认不开 gzip，等于把 214 KB 明文往一条 8 KB/s 的管子里灌。

### 四层修复

1. **应用层 gzip**（`console_server.py::_send`）
   nginx 不压就自己压。`Accept-Encoding` 含 gzip 时对文本响应压缩。
   214 KB → 61 KB。

2. **列表接口精简**（`console_server.py::_mat_list`）
   「主要内容」全文有 13 KB/条，列表根本用不上。改成只给 60 字摘要，
   全文留给 `/api/materials/detail`（点开某条时才单独取）。
   「值得借鉴」在列表里只用真假两态，正文同样留到详情。
   214 KB → **27 KB**（gzip 后 9 KB）。

3. **封面缩略图**（`console_server.py::_make_thumb`）
   页面上封面只显示 78×110，原图 30~100 KB。
   加 `?thumb=1` 用 Pillow 生成 156×220 缩略图（78×110 的 2 倍屏），
   缓存在 `data/thumbs/` 下，源文件 mtime 变了自动重做。
   30 KB → **6 KB**。

4. **前端懒加载**（`console_template.html`）
   `<img loading="lazy" decoding="async">`，浏览器只加载视口内的图。
   实测：初始 1 张 → 滚动到底 30 张，全程 0 失败。

### 附带修的两个真 bug

- **封面图 URL 写死根路径**：原来是 `src="/api/materials/cover?..."`，
  跨域部署时打到了 `cxyo.cn` 而不是后端，全部 404。
  改成走 `apiUrl()`。而且 `<img src>` 不能带 `Authorization` 头，
  跨域时 Cookie 又会被 `SameSite=Lax` 拦，所以用后端同样支持的
  `?access=` 查询参数传口令。
- **素材原始件没上传**：服务器上 `原始素材/视频封面/` 是空的
  （台账同步了但 104 张封面图没传），所以接口返回 404「封面不存在」。

### 上传中文文件名的坑

`serv00` 的 locale 是 `C`（`LC_CTYPE="C"`），**tar 会把中文路径变成 `????`**：

```
$ tar -tvf mat_raw.tar
-rw-rw-rw- 0 0 0 60671 Oct 31 00:24 ????/A0Wf4WEpMO.jpg
```

两个坑叠在一起：

- `os.path.join()` 在 Windows 上产生反斜杠，tar 里存成 `视频封面\xxx.jpg`，
  解出来是一整个文件名。**arcname 必须手工拼正斜杠**。
- 即使用了正斜杠，`tar -xf` 照样因为 locale 把中文目录名解成 `????`。

**解法：不用 tar 命令解，用服务器上的 Python 解**（Python 3.11 的
`sys.getfilesystemencoding()` 是 `utf-8`，不受 shell locale 影响）：

```python
import tarfile, os
BASE = "/usr/home/micky/domains/micky.serv00.net/public_python/03_知识库/素材库/原始素材"
with tarfile.open("/usr/home/micky/tmp/mat_raw.tar", "r") as tf:
    for m in tf.getmembers():
        if not m.isfile():
            continue
        target = os.path.join(BASE, m.name.replace("\\", "/"))
        os.makedirs(os.path.dirname(target), exist_ok=True)
        with open(target, "wb") as f:
            f.write(tf.extractfile(m).read())
```

打包时 arcname 也要手工用正斜杠：

```python
arc = sub + "/" + fn          # 不要用 os.path.join
tf.add(fp, arcname=arc)
```

### 顺带发现：`~/tmp` 不存在

`/usr/home/micky/tmp` 没有自动创建，SFTP 传文件会报 `No such file`。
先 `mkdir -p /usr/home/micky/tmp`。

### 效果对比

| 项目 | 修复前 | 修复后 |
|---|---|---|
| `/api/materials/list` 传输量 | 214 KB | 9 KB（gzip） |
| `/api/materials/list` 耗时 | 24 s | 3.6 s |
| 单张封面图 | 30 KB / 6.5 s | 6 KB / 1.3 s |
| 素材库渲染 | 空白 | 178 条全出，封面懒加载正常 |

## 十一、GitHub 推送的两条路

代理对 `github.com` 的 git 协议（smart HTTP）经常抽风：

- `schannel: failed to receive handshake, SSL/TLS connection failed`
- `CONNECT tunnel failed, response 502`

但 `api.github.com` 通常是通的。所以：

| 方式 | 可靠性 | 用途 |
|---|---|---|
| `git push`（HTTPS） | 看代理脸色，失败率高 | 大批量文件 |
| **GitHub Contents API** | 稳定 | 单个文件更新（推荐） |

Contents API 拿 token 的顺序（注意 WorkBuddy 自带的 PortableGit 里
**没有** `git-credential-manager.exe`，要用系统 Git 的那个）：

```python
# 1) 先试 git credential fill
p = subprocess.run(["git","credential","fill"],
                   input="protocol=https\nhost=github.com\n\n",
                   capture_output=True, text=True)
tok = next((l[9:] for l in p.stdout.splitlines() if l.startswith("password=")), None)

# 2) 拿不到就用系统 GCM
if not tok:
    exe = r"C:\Program Files\Git\mingw64\bin\git-credential-manager.exe"
    p = subprocess.run([exe,"get"],
                       input="protocol=https\nhost=github.com\n\n",
                       capture_output=True, text=True)
    tok = next((l[9:] for l in p.stdout.splitlines() if l.startswith("password=")), None)
```

更新单个文件（先 GET 拿 sha，再 PUT）：

```python
import base64, urllib.parse
path = urllib.parse.quote("08_可运行系统/staff/console_server.py")
_, d = gh("GET", f"https://api.github.com/repos/cxyo/opc/contents/{path}")
payload = {"message": "perf: ...", "branch": "main",
           "content": base64.b64encode(open(local, "rb").read()).decode()}
if d.get("sha"):
    payload["sha"] = d["sha"]
gh("PUT", f"https://api.github.com/repos/cxyo/opc/contents/{path}", payload)
```

推完静态页要记得触发 Pages 构建：

```python
gh("POST", "https://api.github.com/repos/cxyo/opc/pages/builds")
```

验证是否已生效（不要只看 `git ls-remote`，代理会缓存）：

```bash
curl -s -L https://cxyo.cn/opc/ | grep -c "thumb=1"
```

### Pages CDN 缓存

`cxyo.cn` 前面挂了 CDN（`X-Cache: HIT`，`max-age=600`），
推完新代码后**浏览器可能还是旧版**。验证时用全新的 Chrome profile，
或加 `Cache-Control: no-cache` 请求头。

## 十二、验收清单

每次改完线上代码，按这个顺序过一遍：

```bash
# 1. 后端接口
curl -s "https://micky.serv00.net/api/board" -H "Authorization: Bearer $TOKEN"
# 2. 无 token 必须 401（别把系统裸奔出去）
curl -s -o /dev/null -w "%{http_code}\n" "https://micky.serv00.net/api/board"
# 3. 静态页已更新
curl -s -L https://cxyo.cn/opc/ | grep -c "thumb=1"
# 4. 无头 Chrome 实测（登录 → 点页签 → 数卡片）
```

无头 Chrome 脚本要点（踩过的坑）：

- 用 `import` 而不是 `require`（`.mjs` 是 ESM）
- WebSocket 用 `addEventListener('message', ...)`，
  不用 `.onmessage`（原生 WebSocket 的事件 API 不一样）
- `--user-data-dir` 必须用**纯 ASCII 路径**，中文路径 Chrome 起不来
- 页面里的口令框 id 是 `#staff_pwd_in`，不是 `#p`
- 页签选择器是 `button.tab[data-p="p13"]`，
  按文字找会点到卡片里的岗位名
