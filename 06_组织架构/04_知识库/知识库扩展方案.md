# 知识库扩展方案

> 配套文档：`../00_总纲_全自动化组织设计.md`
> 目标：把 14 个岗位的产出，映射到现有 `03_知识库/` 三层结构里，**不新建体系**。

---

## 一、核心原则

**不新建知识库。** 你现有的 `raw / wiki / outputs` 三层结构是对的，本方案只做扩展。

现有结构回顾：
```
03_知识库/
├── 00_Inbox/          临时收集
├── raw/               原始素材，只进不改
├── wiki/              提炼后的知识（9 个分类）
└── outputs/           成品产出
```

**扩展方式**：新增 2 个 wiki 分类 + 3 个 outputs 子目录 + 1 个状态文件。**不加新的一级目录。**

## 三、outputs 层扩展

```
outputs/
├── 文章初稿/                    ← 已有
├── 多平台版本/                  ← 已有
├── 数据复盘/                    ← 已有
├── 质检报告/                    ← 新建：每篇的质检存档
├── 发布记录/                    ← 新建：publish_log
└── 商品数据/                    ← 新建：上架与成交记录
```

### 质检报告存档（`outputs/质检报告/`）

**为什么要存档**：这是**优化质检官的训练数据**。

```
质检报告/
└── 2026-10-27_AI提效选题/
    ├── 01_初稿.md
    ├── 01_质检报告.md
    ├── 02_改稿.md
    ├── 02_质检报告.md
    └── 03_定稿.md
```

**价值**：
1. 出问题时能追溯"哪一版、哪条问题"
2. **积累 20 篇后，可以统计"质检官最常报什么问题"**，从而优化撰稿提示词
3. 这些是真实的评估集（evaluation set）——**每次改提示词都跑一遍，看是不是改好了**

### publish_log（`outputs/发布记录/`）

**结构化数据用表格，不进知识库。** 推荐用 CSV 或扣子数据库：

| 字段 | 说明 |
|------|------|
| publish_id | 唯一 ID |
| topic_id | 关联选题 |
| platform | 公众号/小红书/抖音/闲鱼 |
| published_at | 发布时间 |
| title | 标题 |
| url | 发布链接 |
| content_id | 平台返回的内容 ID |
| status | 成功/失败 |
| error_detail | 失败原因 |
| effect_key | **幂等键** = topic_id + "_" + platform |

**为什么 publish_log 必须在知识库之外**：
它是**结构化、持续追加、需要被程序查询**的数据。放进 wiki 的 Markdown 知识库里，Agent 检索会把它当自然语言读，效率低且容易出错。

## 四、新增状态文件

### `03_知识库/state/`

**这是新增的唯一一个目录**，存放系统的运行时状态：

```
state/
├── 选题池.csv              选题 + 表现分
├── publish_log.csv         发布记录
├── run_status.json         当前运行状态（哪些工作流在跑/在等）
├── pending_approval.json   待人工审批队列
├── cost_log.csv            成本记录
└── 对标账号清单.md          抓取白名单
```

### 为什么需要 state 目录

**关键原因**：这些是**不能被 Agent 随意修改**的数据。

| 数据 | 谁写 | 谁读 | 为什么特殊 |
|------|------|------|-----------|
| `pending_approval.json` | 系统 | 你 | **人工闸的队列**，误改会导致跳过审核 |
| `run_status.json` | 系统 | 系统 | 断点续跑的依据 |
| `cost_log.csv` | 系统 | 你 | 成本核算 |
| `publish_log.csv` | 系统 | 发布官 | **幂等依据**，误改会导致重复发布 |

**规则**：state 目录里的文件**只由对应系统写入，人不手改**（要看就复制出来看）。

## 六、Inbox 的正确用法

### 关键设计

**Inbox 只有一个用途：让你 3 秒内记下任何东西，不需要整理。**

```
你看到一条好内容 → 复制链接 → 丢进 00_Inbox/ → 完事
```

**不要求写任何说明。** 标题能看出来就行。

### 为什么这样设计

整理素材是消耗意志力最重的动作。如果每次收集都要整理，你就停止收集了。**把整理推迟到每周一次，且由 AI 做。**

### 每周清理流程

```
周一 08:45 素材官自动运行：
① 扫描 Inbox 全部文件
② 分类 → 生成卡片 → 写入 wiki
③ 归档无价值的
④ 清空 Inbox
```

**Inbox 每周必须清空。** 积压的 Inbox 会让人逃避整个系统。

## 七、日常维护节奏

| 频率 | 动作 | 谁做 |
|------|------|------|
| 每天（早上） | 选题、撰稿、发布 | 系统 + 你 |
| 每天（晚上） | 素材丢 Inbox + 记一条真实洞察 | 你 |
| 每周一 | 规则差异比对 + Inbox 清理 + 选题筛选 | 安全官 + 素材官 + 你 |
| 每周日 | 复盘 + 调试提示词存入 06_ | 复盘官 + 你 |
| 每月 1 号 | 政策更新 + 禁区审计 + 成本复盘 | 政策官 + 你 |
| 每季度 | 知识库结构盘点 + 归档 | 你 |

### 每月审计要查什么

1. **矛盾** —— 两张卡片说的冲突吗？
2. **出处** —— 每条方法论能说清来源吗？
3. **过时** —— 平台规则、工具价格、模型名还准吗？
4. **冗余** —— 有没有两张卡片说同一件事？
5. **缺口** —— 最近 3 篇文章缺了什么素材？
6. **禁区有效性** —— 禁区条目有没有已经失效的？有没有新增的？

审计报告存入 `outputs/`，**你确认后再改 wiki**。不要让 AI 直接改知识库。
