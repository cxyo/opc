# 技术选型与架构实现

> 配套文档：`../00_总纲_全自动化组织设计.md`
> 目标：把 14 个岗位跑在可靠的编排层上，成本可控、失败可恢复、随时可降级。

---

## 一、技术选型总表

| 层次 | 选型 | 理由 | 优先级 |
|------|------|------|--------|
| 编排引擎 | **扣子（Coze）** | 你已在用；原生支持定时触发、知识库、节点级错误标记、多平台发布 | P0 |
| 跨平台自动化 | **n8n** | 需要跨系统调度时再上。**不要一开始就上**——多一个系统多一份维护 | P3 |
| 长期记忆 | **本地 Markdown 知识库**（`03_知识库/`） | 你已有这套结构。Agent 只读索引，Agent 只写指定目录 | P0 |
| 模型 | **DeepSeek-V3 / R1**（扣子原生） | 不用自己填 API Key。V3 应付绝大多数任务，R1 只给质检 | P0 |
| 通知 | **微信 / 飞书** | 接收告警、待办、日报 | P0 |
| 兜底调度 | **GitHub Actions** | 你已有 3 个定时项目在跑，cron 兜底方案成熟 | P2 |
| 数据存储 | **扣子数据库 / 本地 JSON** | publish_log 这类结构化数据用表格，不进知识库 | P1 |

### 为什么不做"全自建"

调研 2026 年的行业共识，稳定的单人 Agent 系统有三个关键特征：**单一规范状态、中心编排平面、清晰的人工检查点**。

> "Prioritize a single canonical state and a centralized orchestration plane when starting. Those provide predictable leverage for solo operators."

这正是扣子工作流 + 本地知识库的组合。**不要为了"更可控"去自建一套 Python 编排层**——那是把 2 周的维护成本换 0 收益。

## 二、编排架构

### 2.1 三条工作流（不要做成一条）

**关键设计决策**：按**触发方式**分三条工作流，而不是按岗位分。

```
工作流 A：每日情报链（定时，全自动）
  06:30 安全官 → 07:00 政策官 → 08:30 选题官 → 08:45 素材官
  输出：今日情报库 + 选题池 + 待处理素材
  触发：定时，无需人工

工作流 B：内容生产链（手动触发，关键路径）
  你选题 → 拆解 → 撰写 → 质检 → 改稿 → 去AI味 → 质检复检 → 你确认
  触发：你点"运行"，或从选题池点某个选题
  含 2 个人工闸

工作流 C：发布与复盘链（定时 + 事件）
  发布（事件触发：工作流 B 完成）→ 次日 09:00 复盘官
  触发：工作流 B 结束自动触发 + 次日定时
```

**为什么分三条**：
- A 失败不影响 B（情报晚一天不致命）
- B 中断不影响 A（不会因为一个稿子卡住就停整个系统）
- C 的复盘独立，即使发布失败也能记录"这次没发出去"

**如果你把所有 14 个岗位串成一条工作流**，任何一环卡住整条停摆。**这是最常见的架构错误。**

### 2.2 变量命名规范

所有工作流统一使用这套命名，避免跨流程引用混乱：

| 变量 | 类型 | 说明 |
|------|------|------|
| `topic_id` | String | 选题唯一 ID，格式 `20261027-001` |
| `topic` | String | 选题标题 |
| `platforms` | Array | 目标平台列表 |
| `draft` | String | 初稿全文 |
| `qc_report` | String | 质检报告 |
| `human_edit` | String | 改稿后全文 |
| `dedup_draft` | String | 去AI味后全文 |
| `final_article` | String | 定稿 |
| `publish_log_id` | String | 发布记录 ID |

**规则**：变量名**永不手打**，一律从变量面板点选。

## 三、定时任务配置

### 3.1 时间表

| 时间 | 工作流 | 岗位 | 预计耗时 | 成本 |
|------|--------|------|---------|------|
| 06:30 | A | 安全官（规则比对） | 3 min | 低 |
| 07:00 | A | 政策官（政策检查） | 5 min | 中 |
| 08:30 | A | 选题官 | 4 min | 高 |
| 08:45 | A | 素材官（Inbox 整理） | 3 min | 低 |
| 09:00 | C | 复盘官 | 3 min | 低 |
| 15:00 | A | 情报官（午后） | 3 min | 低 |
| 20:00 | A | 情报官（晚间）+ 流量官 | 5 min | 中 |
| 21:00 | A | 情报官（夜间） | 3 min | 低 |
| 周一 10:00 | A | 安全官（周度规则比对） | 5 min | 中 |
| 每月 1 号 | A | 政策官（月度政策） | 10 min | 中 |

### 3.2 成本估算

| 岗位类型 | 单次成本（估算） | 日频次 | 日成本 |
|---------|----------------|-------|--------|
| 便宜模型（扫描/比对） | ¥0.01-0.05 | 8-10 次 | ¥0.1-0.5 |
| 强模型（创作/质检） | ¥0.1-0.5 | 3-5 次 | ¥0.3-2.5 |
| **日合计** | | | **¥0.5-3** |
| **月合计** | | | **¥15-90** |

**这个数字很关键**：自动化一天 3 块以内，一个月 90 块以内。**如果超了，说明有岗位在空转，去看频次上限表。**

### 3.3 预算护栏

```
日调用 > 30 次  → 告警
日调用 > 60 次  → 自动停非必要任务（情报官晚间档、流量官）
周成本 > ¥300   → 告警 + 人 review
```

## 四、发布自动化（最需要小心的一环）

### 4.1 扣子多平台发布配置

搜索到的实操路径：

```
扣子后台 → 左侧「平台管理」→「添加平台」
依次选择：微信公众号、小红书、抖音、今日头条
按提示完成 OAuth 授权
```

> **⚠️ 关键坑（必读）**：
> 微信公众号需提前在「公众号平台→开发管理→基本配置」中填写扣子提供的**域名白名单和 IP 白名单**。
> **未完成此步会导致后续发布失败且无明确报错。**

这是最耗时的排障点。建议在配置当天就发一篇测试内容验证整条链路。

### 4.2 发布限速（必须设）

| 账号阶段 | 发布频率 | 每日上限 |
|---------|---------|---------|
| 新号（0-30 天） | 1 篇 / 2 天 | 1 |
| 稳定期 | 1 篇 / 天 | 1 |
| 多平台 | 各平台独立计数 | 每平台 1 |

**同时发布的间隔 ≥ 2 小时**。一次发 4 个平台在 5 分钟内完成，是典型的异常特征。

### 4.3 幂等与重复发布防护

**这是行业实践里最强调的一点**：

> "An attempt identifier should be new on every try. An effect identifier should remain stable across every attempt to do the same business thing."

对发布场景的具体做法：

```
effect_key = topic_id + "_" + platform
```

**同一个 `effect_key` 永不重复发布**。发布前先查 publish_log：
- 已有记录且状态=成功 → **跳过**
- 已有记录且状态=失败 → 重试（最多 2 次）
- 无记录 → 正常发布

### 4.4 发布后的静默期

**发布后 2 小时内**：不删除、不重发、不修改、不反复刷新查看。
理由：高频操作会被判定为异常运营行为。**这一条比很多技巧都重要。**

## 五、失败恢复机制

### 5.1 失败分类（必须先分类再处理）

**关键原则：不是所有错误都该重试。**

| 类型 | 例子 | 处理 |
|------|------|------|
| 瞬时错误 | 网络超时、限流 | 重试（指数退避，最多 3 次） |
| 语义错误 | 格式不对、变量引用失败 | **不重试**，打回上一步 |
| 系统性错误 | 禁区清单加载失败、模型不可用 | **停止流程 + 告警**，等人处理 |

> "A retry cannot fix missing permissions or a broken API. Classify failures first."

### 5.2 检查点机制

工作流每完成一个节点存一次状态。失败时**从最近的成功点继续**，不从头重跑。

```
N1 ✓ → N2 ✓ → N3 ✗(语义错误)
                ↓
        停在 N3，人工修正后从 N3 继续
        N1/N2 的结果直接复用（省 token，也避免结果漂移）
```

**何时需要检查点**：工作流超过 10 步或 10 分钟，或单次运行成本超过 ¥0.5。你的内容生产链已经够长，**必须有**。

### 5.3 熔断（circuit breaker）

```
阈值：连续 5 次失败 或 60 秒内失败率 > 50%
动作：停止调用该服务 → 通知负责人 → 已运行的任务降级或暂停
```

**为什么需要**：一个依赖挂了，如果没有熔断，会变成"所有任务同时重试 → 雪崩 → 烧完预算"。

**你的系统里最需要熔断的是**：禁区清单加载（质检官）、模型 API（全部）。

## 六、观测性

### 6.1 必须记录的字段

每次工作流运行记录：

```
run_id            运行唯一 ID
topic_id          关联选题
workflow_name     哪条工作流
started_at / ended_at
status            成功/失败/中止/待人工
nodes_total / nodes_ok / nodes_failed
model_calls       模型调用次数
tokens_total      总 token
cost_estimate     估算成本
decision_points   人工闸的决策记录（谁/何时/选了什么/理由）
error_detail      失败节点的错误信息
```

### 6.2 三条必问的问题

系统跑起来后，你要能随时回答：

1. **它现在在干什么？** → 看 run 状态表
2. **它在等什么？** → 看 pending approval 列表
3. **这周花了多少钱？** → 看成本统计

**答不上来这三个问题，就不要扩大自动化范围。**

## 七、分阶段落地

### P0（1-7 天）：安全底座

**目标**：禁区能查、质检能跑

- [ ] 建 `03_知识库/wiki/10_禁区/` 并把两个禁区清单放进去
- [ ] 写质检官提示词（见 A10 说明书）
- [ ] **人工跑 10 篇质检**，标出违规/AI味/错误 → 这 10 篇是质检基线
- [ ] 在扣子建质检 Agent（只挂禁区知识库）
- [ ] 验证：拿一篇有问题的稿子测，确认能查出来

**验收标准**：质检官能准确指出你已知的 8 处以上问题。

### P1（8-20 天）：单线跑通

**目标**：一篇内容走完全流程

- [ ] 扣子建工作流 B（内容生产链）
- [ ] 把现有 6 个 Agent 提示词接进去
- [ ] 加质检节点 + 2 个人工闸
- [ ] 手动跑通 3 篇
- [ ] **配 publish_log 记录**
- [ ] 建复盘 Agent（先手动喂数据）

**验收标准**：3 篇发布成功，每篇有质检报告和复盘记录。

### P2（21-35 天）：情报自动化

**目标**：早上起来选题池已备好

- [ ] 建工作流 A（每日情报链）
- [ ] 配置 4 个定时任务（情报/政策/选题/素材）
- [ ] 建对标账号清单（≥10 个）
- [ ] 配通知通道

**验收标准**：连续 7 天自动产出选题，每天 ≥3 个候选。

### P3（36-50 天）：多平台发布

**目标**：一稿多发

- [ ] 扣子平台管理绑定 4 个平台
- [ ] **先做公众号白名单配置并测试**
- [ ] 配发布限速 + 幂等检查
- [ ] 建工作流 C

**验收标准**：一稿四发成功，publish_log 完整，**无重复发布**。

### P4（51-70 天）：闭环成型

**目标**：系统开始自学习

- [ ] 复盘官自动拉数据
- [ ] 表现分写入选题池
- [ ] 流量官出周报
- [ ] 建成本监控

**验收标准**：选题官会优先推荐历史上表现好的类型。

### P5（71-90 天）：商业闭环

**目标**：流量能变成钱

- [ ] 商品官上线（资料包上架）
- [ ] 售后官上线（FAQ 库）
- [ ] 私域承接流程打通
- [ ] 询盘 → 成交 → 交付 → 复购 全链路

## 八、排障速查表

| 现象 | 最可能原因 | 解法 |
|------|-----------|------|
| 公众号发布失败，无报错 | **域名/IP 白名单没配** | 公众号后台 → 开发管理 → 基本配置 → 填扣子提供的白名单 |
| 节点引用不到变量 | 手打了变量名 | 从变量面板点选 |
| 知识库召回不到 | 文件没解析完 | 等 1-5 分钟；查解析方式是"精准解析" |
| 定时任务不触发 | 触发器未启用 / 额度限制 | 检查触发器状态；用飞书/第三方 cron 兜底 |
| 质检官查不出问题 | 禁区清单没挂进知识库 | 检查 Bot 的"知识"区 |
| 发布后看不到 | 平台审核延迟 | 正常，等 1-2 小时 |
| 重复发布 | 幂等键失效 | 检查 publish_log 是否在发布前被读取 |
| 工作流跑到一半停 | 触发人工闸（正常） | 去审批队列处理 |
| 模型调用次数暴增 | 无检查点，失败重跑 | 加检查点，从最近成功点恢复 |

## 九、什么时候该停下来

**以下任一情况出现，立刻把自动化降回 L2：**

- [ ] 连续 3 篇内容质检不通过
- [ ] 账号收到平台警告（哪怕是轻微提醒）
- [ ] 单日成本超预算 2 倍
- [ ] 复盘数据显示内容质量在下降（说明流水线本身出了问题）
- [ ] 你开始"看不懂"系统在干什么

**最后一条最重要。** 一个你看不懂的系统，出问题时你也救不了它。
