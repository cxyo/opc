## 一、岗位职责

**一句话**：把老板微信里几千条聊天记录，自动整理成「客户到哪一步了、供应商货到哪了、我的人跑了几个客户」的看板。

它不生产内容，生产**经营事实**。

---

## 二、为什么需要这个岗位

老板每天真正要知道的三个问题，散落在几千条聊天记录里，靠人翻根本翻不动：

| 问题 | 现在怎么答 | 这个岗位怎么答 |
|---|---|---|
| 哪个客户推到哪一步了 | 翻聊天记录，或者干脆忘了 | 客户线：进展阶段 + 卡点 + 最后活跃 |
| 哪个供应商的货到哪了、款付了没 | 打电话问 | 供应商线：货的阶段 + 款的阶段 |
| 我这几个员工分别跑了几个客户 | 凭印象 | 内部线：每人对接客户数、拜访次数、动作分布 |

ToB 业务里，一个客户从"初步接触到"签合同"可能跨三个月。
聊天记录是唯一的事实来源，但它没人读。

## 三、六条硬规则

| 编号 | 规则 | 为什么 |
|---|---|---|
| R1 | 只读本机自己微信账号，原始记录**不上传**，密钥不出本机 | 聊天记录是最敏感的数据。泄露一次就全盘输 |
| R2 | 私人/社交/学习/服务方会话**自动排除**，不进业务视图 | 老板的私人聊天不该出现在给客户看的系统里 |
| R3 | 判不准的会话进「待人工确认」，**不替老板猜** | 假结论比没结论更贵 —— 老板会照着假结论做决策 |
| R4 | 每条结论都带**原文出处**（时间 + 原话片段） | 没有出处的结论，老板没法验证，也不敢用 |
| R5 | 聊天里没提的事，写「未在聊天中提及」，**不推断** | "他没回消息"不等于"他不满意" |
| R6 | 只陈述事实，不做绩效评价 | "某人开发客户 3 个"是事实；"某人业绩不行"是评价 —— 后者不做 |

## 四、数据来源与实现路径

### 4.1 为什么必须自己解密

微信 4.x 的聊天记录存在 WCDB（SQLCipher 4 加密）里，官方不提供读取接口。
现有方案是 wx-cli（Mac 端），Windows 没有等价物。

本岗位的路径：

```
① 内存提取密钥
   静态串 com.Tencent.WCDB.Config.Cipher 作路标
   → 顺 std::string 节点 → 配置对象 → Data blob
   → 与 32 字节固定掩码异或 → x'<96hex>'
   一次拿到 39 个候选

② 匹配到具体库
   28 个库各有独立密钥 → 逐库验证 SQLCipher 4 HMAC

③ 解密
   页布局 [salt 16][密文 4000][IV 16][HMAC 64]，reserve=80
   mac_salt = salt ⊕ 0x3A
   mac_key = PBKDF2-HMAC-SHA512(enc_key, mac_salt, 2 轮)
   HMAC-SHA512(mac_key, page[16:4032] + 页号4字节LE)
```

**实测结果**：28/28 库解密成功，`integrity_check` 全 ok，93856 条消息全部读出。

### 4.2 关键技术点（踩过的坑）

| 坑 | 现象 | 解法 |
|---|---|---|
| 32 位地址上限 | 内存只读到 0.1MB，误判为权限不足 | `MAX_ADDR = 0x7FFFFFFFFFFF` + 显式声明 argtypes/restype |
| 密钥被 XOR 编码 | 正则扫 `x'<96hex>'` 870MB 零命中 | 改走路标→指针链→异或解码 |
| 保留字节被改 | 解密后 `database disk image is malformed` | 保留 SQLite 头原字段，只把 salt 段还原成 magic |
| 表名是 bytes | `text_factory=bytes` 让统计恒为 0 | 拼 SQL 前用 `_s()` 转 str |
| 表名不是 `Msg_<session_id>` | 201 个会话读出 0 条消息 | 实际是 `Msg_<md5(username)>` |
| 分片库 | 同一会话分散在 6 个库 | 遍历所有库合并，按时间排序 |
| zstd 压缩消息 | 纯文本读不出 | 魔数 `28b52ffd` 检测后解压 |

## 五、关系识别规则

### 5.1 五类信号加权

| 信号 | 权重 | 说明 |
|---|---|---|
| 备注标签 | 3.0 | 用户自己打的备注最准（「力生客户」「服务器供应商」） |
| 昵称含公司/部门 | 2.0 | 「韩磊（力生激光切割打磨机器人）」→ 同事 |
| 群名关键词 | 2.5 | 「外包安装沟通群」→ 供应商 |
| 群成员重叠 | 1.0 + 0.4×人数 | 群里有多位公司标识成员 → 内部群 |
| 消息内容 | 1.0 × 密度系数 | 需命中 ≥3 个或命中强业务词 |

### 5.2 供应商判定：交易型 vs 品类型

**这是最容易错的一条线**。实测踩坑：

- 「陈泽锋」（力生技术同事）聊 PLC、传感器、机器人 → 被误判供应商
- 根因：这些是**品类词**，是力生**自己造的东西**，同事聊自家产品在正常不过

解法：拆成两档

| 档 | 词表 | 权重 | 例子 |
|---|---|---|---|
| 交易型 | 进货/采购/货期/交期/对账/月结/送货单/开票 | 高（≥2 个才算数） | 说明对方在卖货给我们 |
| 品类型 | PLC/伺服/电机/机械臂/打磨机 | 低（×0.25） | 只是聊到了这类东西 |

外加**硬门槛**：供应商必须命中强特征（名称/备注含"供应商/厂商/货源"、
群名含外包类、或 ≥2 个交易信号），否则降级「待人工确认」。
**宁可让老板补一次，也别给假结论。**

### 5.3 排除规则

| 类别 | 命中词举例 |
|---|---|
| 私人 | 爸爸/妈妈/老婆/哥哥/家人/亲戚/同学/邻居 |
| 社交 | 相亲相爱/家族/旅游/广场舞/钓鱼/麻将 |
| 学习 | 资料库/工具库/课程/弟子班/助教/学员/打卡群 |
| 服务方 | 职业规划/规划师/客服/培训/讲师/老师/导师/招生 |
| 系统 | 微信团队/服务通知/文件传输助手 |

## 六、阶段与卡点抽取

### 6.1 阶段按时间序判定（不按词表顺序）

业务是**向前推进**的：询价 → 下单 → 打样 → 生产 → 到货 → 安装调试。

如果按词表顺序取「最后一个命中的」，早期说"已下单"、后期说"已到货"，
会报"已下单" —— 等于告诉老板进度**倒退**了。

**解法**：`_stage_by_time()` 扫消息时记录每个阶段**首次出现**的时间，
按时间排序，最后一个就是当前阶段。

### 6.2 阶段词表

| 线 | 阶段 |
|---|---|
| 供应商货 | 询价中 → 洽谈中 → 已下单 → 打样中 → 已打样 → 生产中 → 安装调试中 → 已交付 |
| 供应商款 | 待付款 → 已付定金 → 已对账 → 已付尾款 → 已结清 |
| 客户进展 | 初步接触 → 需求确认 → 方案沟通 → 报价中 → 打样验证 → 商务谈判 → 成交 |

### 6.3 卡点分类（8 类）

预算不足 / 排期冲突 / 技术问题 / 决策未定 / 需求变更 / 付款问题 /
联系方式不畅 / 产能不足

每条卡点都带命中词和原文片段。

## 七、内部员工线：跨会话关联

「对接客户数」是最容易算错的指标。**只在内部会话里统计必然恒为 0** ——
客户会话永远不会进入内部会话集合。

**正确做法**：

```
① 建 uid → 员工名 表
   来源 A：内部私聊会话的 username（私聊的 username 就是同事本人）
   来源 B：联系人表里备注/昵称带公司标识的（覆盖只在客户群出现的同事）

② 扫客户/供应商会话
   消息发送者命中 ① → 这位同事在对接这个客户

③ 动作统计
   覆盖两处：他自己的内部会话 + 他在客户会话里的发言
```

## 九、运行方式

```bash
# 首次：解密微信数据库（28 个库，约 2 分钟）
python tools/提取微信密钥.py
python tools/wechat_decrypt.py

# 每日同步（零 token 零费用，可挂 Windows 计划任务）
python run.py daily-sync

# 查看状态
python run.py wechat status

# 导出简报
python run.py wechat export

# 看某个会话明细
python run.py wechat detail --session <username>
```

## 十、性能与缓存

| 项 | 数值 |
|---|---|
| 源库数量 | 28 个（全部解密成功） |
| 消息总量 | 93856 条 |
| 消息表 | 297 张 |
| 会话索引 | 1144 个（308 个近期 + 历史合并） |
| 有消息会话 | 201 个 |
| 全量分析耗时 | 约 75~125 秒 |
| 缓存命中 | 源库指纹 + **LOGIC_VERSION** |

**LOGIC_VERSION 的意义**：源库指纹只反映"数据变没变"，但**代码变了**
结果也会变。只比源库指纹的话，改完规则系统会拿旧缓存糊弄过去。
把逻辑版本号放进指纹里，代码一改就自动重算。

## 十一、失败处理

| 情况 | 行为 |
|---|---|
| 微信没登录 / 库不存在 | 明确报「数据还没解密」，不返回空结果假装没事 |
| 数据库未解密 | 提示先跑解密流程，给出命令 |
| 密钥提取失败 | 报「没找到密钥」，说明微信版本可能变了 |
| 部分库解密失败 | 其余库照常分析，失败清单单独报 |
| 分类置信度低 | 进「待人工确认」，不硬塞进客户线 |
