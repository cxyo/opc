# 一人AI公司 · 全自动化组织设计规划

> 版本：v1.0 · 2026-10-27
> 目标：把「一个人 + 多个 AI 员工」变成一条能持续跑的产线，从选题到成交全流程闭环。
> 本文档是总纲，下挂 4 份子文档：岗位说明书 / 禁区与合规 / 技术实现 / 知识库设计。

---

## 零、先说清楚：什么叫"全自动化"

**这句话需要先拆开，因为它是最容易被误解的部分。**

我搜了一圈 2026 年的行业共识，结论很一致：

> Agent 能打破的是**规模**——1 人 + 10 个 Agent 可以超过 10 人团队，24×7 不间断。
> Agent 打不破的是**判断力、信任关系、质量把控**——客户买的还是"人"，Agent 是放大器不是替代者。

所以"最终实现全自动化"这个目标，我建议改成：

### 三级自动化模型（L1 / L2 / L3）

| 级别 | 定义 | 适合的环节 | 你要做的 |
|------|------|-----------|---------|
| **L3 纯人工** | 人做，AI 只给建议 | 首次发布重要内容、涉及金额的成交回复、平台申诉 | 上手期全是 L3 |
| **L2 半自动** | AI 产出，人确认后执行 | 日常内容生产、选题、质检、多平台改写 | **主力模式** |
| **L1 全自动** | AI 跑完整链路，人只看结果 | 数据采集、规则差异比对、数据复盘、周报 | 稳定后才开 |

**这个设计的价值在于：你能随时降级。**

扣子平台规则一变、某个 Agent 抽风、平台临时收紧——把某个环节从 L1 拉回 L2，只需要改一个开关，不需要重建系统。**这是自动化系统唯一真正重要的保险丝。**

### 必须永久保留人工的三道闸

即使将来全 L1，这三道也不能省：

1. **首次发布闸**——新账号前 10 篇内容，每篇必须人看过再发
2. **成交闸**——涉及金额、承诺、退款的人工回复
3. **申诉闸**——平台判定违规后的申诉，只能人写

**理由**：账号是全部前期投入的载体。封号的损失是不可逆的，而"多花 3 分钟看一眼"的成本是可逆的。这笔账永远划算。

## 一、原框架的评审：7 个结构性问题

你的十部门框架（安全员 / 国家政策 / 信息源 / 素材库 / 创作中心 / 去AI味 / 检测中心 / 发布规则 / 流量中心 / 售后中心）**覆盖度很好，方向全对**。问题出在结构层。

### 问题 1：部门是并列的，缺少依赖顺序

**现象**：安全员和检测中心都在"事后"，而违规内容写完再改，成本是发现时机的十倍。

**修正**：改为**五层流水线**，安全员不是一个"部门"，而是**每一层的入口过滤器**。

```
┌─────────────────────────────────────────────────┐
│  L0 约束层（横向贯穿所有层）                      │
│  安全官 · 政策官 · 规则库（禁线清单）              │
│  ↓ 每层入口都要过一遍                             │
├─────────────────────────────────────────────────┤
│  L1 输入层：情报官 · 素材官 · 选题官              │
│     ↑ 外部世界 → 结构化情报                       │
├─────────────────────────────────────────────────┤
│  L2 生产层：拆解官 · 撰稿官 · 改稿官 · 去AI味官   │
│     ↑ 情报 + 知识库 → 成稿                        │
├─────────────────────────────────────────────────┤
│  L3 检测层：质检官（违规/AI味/错误 三合一）        │
│     ↑ 成稿 → 通过 / 打回                          │
├─────────────────────────────────────────────────┤
│  L4 分发层：发布官 · 流量官                       │
│     ↑ 通过 → 多平台发布 → 数据回收                │
├─────────────────────────────────────────────────┤
│  L5 闭环层：复盘官 · 售后官                        │
│     ↑ 数据 → 结论 → 回流到 L1 选题                │
└─────────────────────────────────────────────────┘
              L0 约束层始终横切，全程生效
```

### 问题 2："自动获取平台最新规则"这条路径走不通

**你的设想**：Agent 自动抓取平台规则 → 有改动就同步 → 写进禁区。

**为什么不行**（这是本次调研最关键的发现）：

1. **平台规则不都在公开页面**。小红书的《社区公约2.0》在 App 内和创作者后台，闲鱼的治理公告在「闲鱼黑板报」公众号，抖音的在「抖音黑板报」——**大量在 App/公众号内，抓取本身就可能违反 robots 或用户协议**
2. **规则改动的粒度极细**。闲鱼 2026-10-23 刚发的公告，禁的是"恶俗玩梗类商品"里"以报复平事为卖点的服务"。这种颗粒度，AI 从网页标题里判断不出来
3. **误判成本不对称**。漏掉一条红线 = 封号；误加一条假红线 = 少写一个选题，损失一个内容位

**修正方案**：

| 环节 | 谁做 | 怎么做 | 频率 |
|------|------|--------|------|
| 情报收集 | **人**（你） | 看到公告就丢进 Inbox，一句话标题即可 | 随时 |
| 差异比对 | **安全官** | 对比新旧规则，输出"新增/收紧/放宽"三段式差异 | 每周 1 次 |
| 禁区更新 | **人确认 + 安全官执行** | 差异表 → 你勾选 → 写入禁区文件 | 每周 1 次 |

**安全官的定位从"抓取者"变成"审计者"**。这个转变让整件事从"不可靠"变成"可靠且省事"——你每周花 10 分钟丢 3 条链接，它帮你比对、提炼、写进禁区。**这才是人机协作该有的样子。**

### 问题 3：去AI味官 与 检测中心 职责重叠

- 「去AI味」= **改写动作**（把 AI 味重写成人味）
- 「检测」= **判定动作**（判断还有没有 AI 味）

两个都叫"去AI味"，边界必然模糊。

**修正**：质检官一个岗位、三项检查（违规 / AI味 / 错误），出**一份合并报告**。去AI味官只管改写，接收质检官的"AI味评分 + 具体位置"。**一进一出，职责清晰。**

### 问题 4：没有数据回流闭环

你的框架里，流量中心说"挖掘更多流量增加曝光率及转化率"，但**发布后的数据去哪了？**

没有回流 = 永远在猜。发了 50 篇不知道哪篇好，下次还是凭直觉选题。

**修正**：新增**复盘官**（L5），职责是发布 24 小时后把数据拉回来，写进案例库，并**反向给选题官打分**。这是整个系统从"自动化"变成"会学习"的关键。

### 问题 5：缺成交与交付环节

流量来了，货在哪？你的框架里"发布规则"提到咸鱼，但**没有商品运营和成交承接**。

**修正**：L5 增加两个岗：
- **商品官**：负责资料包上架、定价、详情页、库存/交付物
- **售后官**：负责 FAQ、答疑、差评处理、复购引导

且**商品官要挂到 L4 分发层**，不是 L5——**发布和上架是同一批动作的两种形态**（内容分发到内容平台，商品分发到交易平台）。

### 问题 6：没有定义自动化的安全阀

见第零章的三级模型。补充关键机制：

| 机制 | 做法 |
|------|------|
| **熔断** | 连续 3 天质检不通过 → 自动降级到 L2 人工模式 + 告警 |
| **发布限速** | 单账号每天最多 1 篇，平台新号期最多 1 篇/2 天 |
| **禁区熔断** | 安全官发现新增红线 → 立刻停发相关选题，进人工确认 |
| **静默期** | 发布后 2 小时内不自动改稿（避免运营动作被判定为异常） |

### 问题 7：成本与配额没设计

10 个部门全量跑，一天可能几十次模型调用。

**修正**——**模型分级**（这是省钱的关键）：

| 任务类型 | 模型 | 举例 |
|---------|------|------|
| 扫描/比对/分类 | 便宜模型（DeepSeek-V3 低温度，或专用小模型） | 规则差异比对、选题初筛、评论分类 |
| 创作/推理 | 强模型（DeepSeek-V3 高温 / R1） | 撰稿、质检、深度拆解 |
| 判定/终审 | 强模型 + 人工 | 首次发布、成交回复 |

**频次上限表**（直接写进每个岗位说明书）：

| 岗位 | 每日调用上限 | 触发方式 |
|------|------------|---------|
| 安全官 | 2 次 | 定时 10:00 + 你手动触发 |
| 情报官 | 3 次 | 定时 9:00/15:00/21:00 |
| 选题官 | 1 次 | 定时 8:30，产出当日选题池 |
| 撰稿官 | 5 次 | 手动触发（按需写） |
| 质检官 | 5 次 | 撰稿后自动触发 |
| 复盘官 | 1 次 | 定时次日 9:00 |

**预算护栏**：日调用超 30 次 → 告警；超 60 次 → 自动停非必要任务。

> 下面这岗是另一条线：**读老板自己的微信聊天记录，把客户/供应商/员工动态
> 自动整理成看板**。它不产内容、不花钱（纯本地），但对 ToB 型业务价值极大。

| 层 | 岗位 | 一句话职责 | 自动化 | 每日上限 | 优先级 |
|----|------|-----------|--------|---------|-------|
| **L1 输入** | **A26 微信情报官** | 微信聊天记录 → 客户/供应商/内部三线看板 + 卡点 + 每日简报 | L2 | 1 | **P0** |
| **L1 输入** | **A25 素材情报官** | 视频/文章 → 可复用素材卡 + 改写引擎 | L2 | 5 | P2 |

**A26 为什么是 P0**：它回答老板每天最关心的三个问题 ——
「哪个客户推到哪一步了」「哪个供应商的货到哪了、款付了没」
「我这几个员工分别跑了几个客户」。这些信息本来散在几千条聊天记录里，
靠人翻根本翻不动。

**边界（必须守住）**：
- 只读本机自己微信账号，原始记录**不上传**，密钥不出本机
- 私人/社交/学习/服务方会话**自动排除**，不进业务视图
- 判不准的会话进「待人工确认」，**不替老板猜**
- 每条结论都带**原文出处**，聊天里没提的事写「未在聊天中提及」

**落地方式**：
```bash
python run.py daily-sync          # 每日同步（零 token 零费用，可挂计划任务）
python run.py wechat export       # 导出老板能直接看的 Markdown 简报
```
控制台页签：**🔍 微信情报**（客户线 / 供应商线 / 内部线 / 卡点与待办 / 待人工确认）

### 2.4 三个必须人工的长期动作

除了日常的确认闸，还有三件**每周/每月**必须人做的事：

| 动作 | 频率 | 原因 |
|------|------|------|
| 禁区审阅（勾选规则差异） | 每周 | AI 只能提建议，判断权在人 |
| 选题池筛选 | 每周 | 判断"这个题值不值得做"是核心能力 |
| 月度系统复盘 | 每月 | 哪些岗位在空转、哪些提示词该重写 |

## 二·五、扩展架构的关键设计约束

新增 6 岗时必须守住的四条，否则扩展会变成风险放大器：

| 约束 | 内容 | 为什么 |
|------|------|-------|
| **1. 无禁区不建岗** | 每个新岗位在创建时必须绑定禁区清单依赖 | 网传清单最大的问题是把岗位当功能罗列，没有风险边界 |
| **2. 自动化等级只升不降** | A18 转化官默认 L3 永久人工，不允许为了效率下调 | 它直接接触钱和客户承诺 |
| **3. 矩阵 ≠ 账号数量对冲** | 同主体下 2-3 个号做不同细分赛道，独立设备、内容差异化、不互相导流 | 平台是**连坐制**——同主体任一账号严重违规，其他矩阵号同步封禁 |
| **4. GEO 优先于打扰式获客** | 触达客户的路径优先选「被找到」而非「去找人」 | 打扰式获客赛道正在被法律和平台双重封堵 |

**关于第 3 条的具体数字**：抖音明确规定矩阵号需**独立设备与独立 IP**、严禁批量搬运重复发布、严禁矩阵互相导流；小红书 2025 上半年封禁黑产账号超 1000 万个、处置 AI 虚假内容超 330 万条；黑产云控系统已能单机控 1 万台手机。**你的账号数不是风控对冲，是连坐放大器。**

## 三、各层怎么落地

### 3.1 L0 约束层 → `02_禁区与合规/`

三个文件：
- `禁区清单_平台红线.md` —— 4 个平台的红线，结构化到可被 Agent 检索
- `禁区清单_国家政策.md` —— AI 创作相关法规 + 鼓励方向
- `规则更新日志.md` —— 每次比对的差异记录

**核心设计**：禁区不是"文档"，是**结构化条目**，每条含：平台 / 生效日期 / 禁止行为 / 处罚后果 / 来源链接 / 判定关键词。

这样质检官才能拿它做**逐条比对**，而不是"参考着写"。

### 3.2 L1 输入层 → 复用现有 `03_知识库/wiki/01_情报` 和 `07_选题与素材`

情报官和素材官本质是"资料管家"的强化版。**不新建体系，扩展现有的。**

### 3.3 L2 生产层 → 复用现有 6 个 Agent 提示词

现有的 `01_Agent提示词/` 里 4 个（拆解/撰写/修改/去AI味）已经对应 L2 的 4 个岗位。**只缺"质检三合一"和"多平台改写"定位调整。**

### 3.4 L3 检测层 → 新建「质检官」

这是最关键的新岗位。三合一检查：
1. **违规检查** —— 对照禁区清单逐条比对
2. **AI 味检查** —— 给评分 + 标出具体位置
3. **事实/错误检查** —— 数字、引用、逻辑矛盾

### 3.5 L4 分发层 → 新建「发布官」+「流量官」

发布官要处理**平台差异**（字数、标签、封面、发布时间）。

### 3.6 L5 闭环层 → 新建「复盘官」+「售后官」

**复盘官是整个系统"会学习"的关键**，见下文 3.7。

### 3.7 数据回流的具体机制

```
发布（10:20）→ 记录 publish_log（平台/时间/标题/链接/内容ID）
     ↓
次日 09:00 复盘官拉数据（阅读/点赞/评论/涨粉/成交）
     ↓
写入 wiki/04_案例库/ + 给选题池打「表现分」
     ↓
选题官下次出选题时，读表现分，优先选高分类型
```

**这就是"复利"的来源**：第 1 篇和第 50 篇的选题质量不同，就是因为第 1-49 篇的数据被回收了。

## 四、技术实现路线

详见 `03_技术实现/技术选型与架构.md`。核心结论先给：

| 层次 | 用什么 | 为什么 |
|------|--------|--------|

| 跨平台自动化 | **n8n** | 需要时再上，扣子优先（少一个系统少一份维护） |
| 长期记忆 | **本地 Markdown 知识库**（现有 `03_知识库/`） | 你已有；Agent 只读索引 |
| 强模型 | **DeepSeek-V3 / R1** | 扣子原生支持，不用自己填 Key |
| 通知 | **微信/飞书** | 接收告警和待办 |
| 兜底 | **GitHub Actions** | 你已有三个定时项目在跑；cron 兜底方案成熟 |

**发布自动化的一条硬约束**（搜索到的实操信息）：

> 微信公众号需提前在「公众号平台→开发管理→基本配置」中填写扣子提供的域名白名单和 IP 白名单，**未完成此步会导致后续发布失败且无明确报错**。

这个坑我写进了技术实现文档的排障表。

## 七、这份规划不承诺什么

- ❌ 不承诺 90 天后完全无人干预——**L2 半自动是长期最优解**
- ❌ 不承诺流量一定涨——**系统能提高的是"内容命中率和迭代速度"，不是"选题必火"**
- ❌ 不承诺零成本——**21 个 Agent 全跑起来有成本，靠模型分级 + 频次上限控制**
- ❌ 不承诺 GEO 排名——**AI 平台回答受多因素影响，提及率波动是常态**
- ❌ 不承诺矩阵号能防封号——**平台是连坐制，矩阵是放大器不是对冲**
- ✅ 承诺：**每一步都可降级、可中断、可回滚**
- ✅ 承诺：**禁区永远优先于效率**——任何时候，安全 > 出货
